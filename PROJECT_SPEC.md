# Специфікація проєкту: Sketch map

**Статус документа:** робоча специфікація, 6 жовтня 2026 року  
**Призначення:** зафіксувати бізнес-вимоги, обмеження, архітектуру та план етапів, щоб продовжувати проєктування без втрати контексту.

## 1. Мета та межі

Створити внутрішній картографічний вебзастосунок для співробітників організації. Користувач має змогу редагувати дозволені об’єкти ArcGIS Feature Services, вибрати робоче завдання, компонувати аркуш A4 та експортувати карту у JPEG із контрольованим масштабом і UTM-сіткою.

Застосунок — клієнтський SPA, розміщений на GitHub Pages. Джерелом карти і сервісів є ArcGIS Enterprise Portal. Авторизація виконується через Portal OAuth/SSO; власний сервер застосунку не планується. Portal і Feature Services залишаються джерелом істини для доступу й даних.

## 3. Робочі сценарії

### 3.1 Вхід і відкриття карти

1. При запуску перевірити збережену автентифікацію Portal.
2. Якщо сесії немає, показати вхід через Portal. Використовувати OAuth authorization code + PKCE (`flowType: auto` на Enterprise 10.9+).
3. Після автентифікації завантажити WebMap і два відображення карти.
4. Помилки Portal, item access, layer metadata, запитів і capabilities показувати користувачу з деталями, очищеними від токенів.

### 3.2 Вибір завдання, фільтрація і навігація

- Завантажити унікальні значення поля `task.task_code`, відсортувати з natural/numeric ordering.
- Після вибору коду знайти GlobalID батьківського `task`.
- Установити view-local фільтр `parentglobalid` на:
  - `evidence`;
  - `taskGeopoint`;
  - `taskPolygon`.
- Отримати GlobalID вибраних task polygons та фільтрувати `polygonGeopoint` через їх `parentglobalid`.
- Для шару task залишити тільки вибраний `task_code`.
- Для `surveyedLine` установити view-local фільтр `task_code = обраний код`; без вибраного завдання фільтр зняти.
- Не змінювати глобально визначення сервісу й не видаляти/перезаписувати авторські display filters; застосунок має зберігати та відновлювати їх.
- Після встановлення фільтрів отримати server-side extent саме відповідних `taskPolygon` і виконати плавний `goTo` у **вкладці редагування**. Відсутність пов’язаних полігонів має бути явно повідомлена.
- Той самий task-контекст застосовується до print view. Print view зберігає незалежний масштаб і рамку листа; при виборі task початково центрується біля відповідної polygon geopoint/області.
- Режим редагування залишає користувачеві вільну навігацію/масштабування.

### 3.3 Редагування

- `topoPoint`, `topoLines`, `topoPolygons`: створення — лише через власний TemplatePicker (клієнтські `layer.templates` класичний Editor ігнорує), оновлення атрибутів і геометрії та видалення — через ArcGIS Editor (створення в ньому вимкнено, щоб не дублювати TemplatePicker), відповідно до сервісних capabilities і поточних privileges.
- `surveyedLine`: створення, оновлення геометрії/атрибутів і видалення через ArcGIS Editor. Якщо вибрано завдання, `task_code` автоматично записується в усі створені/оновлені обʼєкти перед відправкою `applyEdits`; поле `task_code` у формі приховане.
- `evidence`: вибір наявного feature і редагування його атрибутів (`symbol_code`, `symbol_angle`, `legend_decr`); не показувати додавання, видалення, attachment workflow і геометричні інструменти.
- `symbol_angle` (градуси 1–360, порожньо — без повороту): кут повороту точкового знака на карті, 0 — північ, за годинниковою (`rotationType: geographic`); у легенді знаки без повороту. Якщо поля нема в сервісі — колонка лише для перегляду, поворот вимкнено.
- Решта task-шарів read-only.
- Використовувати форми/домени Feature Service, коли вони доступні; перевірити snapping для реальних задач окремо.

## 4. Два види карти та екранна композиція

Застосунок містить дві вкладки:

1. **Редагування** — інтерактивна карта, вільний zoom, task-code filter, списки шарів та `Editor`.
2. **Макет друку** — A4 preview, UTM zone, preset scale, legend, scale bar, UTM grid, координатні підписи та JPEG export.

Обидва `MapView` використовують одну `WebMap`/набір шарів для спільного стану даних, але мають окремі viewport/filter state. Вкладка редагування має вільну навігацію; print MapView має вимкнене обертання, фіксований масштаб зі списку та просторову систему, вибрану користувачем.

На аркуші друку поверх головної карти — інсет-карти: LM завжди (одна точка), BM — по одній на кожну BM-точку завдання (нумерація BM1, BM2… як у штампі). На обох картах видимі полігони завдання, відповідна точка та відфільтровані за `task_code` лінії `surveyedLine`. Дефолт 40×50 мм, розмір тягнеться за правий нижній кут, мінімум 20 мм; та сама WebMap. Центри — відповідні точки, масштаб: LM свій, усі BM — спільний (дефолт 1:1000, зум замкнено, пан вільний), без сітки й підписів, рамка 0.2 мм, позиції тягнуться мишкою. BM-інсет можна вимкнути тоглом у панелі (вимкнений — вʼю знищується); LM без тогла. Без точки інсет ховається.

Висота всього SPA має дорівнювати доступній висоті viewport (`100dvh`), без вертикального розтягнення документа. ArcGIS Editor монтується у власний scroll container; довгі tool/forms прокручуються всередині панелі, а карта та інші області лишаються видимими. На вузькому екрані дозволений responsive document scrolling.

## 5. Макет аркуша і друк

### 5.1 Формат і масштаб

- A4: `210 × 297 мм` (portrait) або `297 × 210 мм` (landscape).
- JPEG у цільовій роздільності 300 dpi: номінально `2480 × 3508 px` portrait, `3508 × 2480 px` landscape (округлення до цілих пікселів).
- Початковий перелік масштабів: `1:100`, `1:200`, `1:500`, `1:1000`, `1:2000`, `1:5000`, `1:10000`, `1:25000`, `1:50000`; його можна конфігурувати.
- Точність масштабу задається для фізичного розміру map frame. Export/print dialog не повинен неявно змінювати map-frame dimensions; для друку на принтері потрібен режим друку «100% / Actual size».
- Зафіксувати відступи сторінки, співвідношення A4, розміщення map frame, legend і scale bar як параметри макета. Легенда та інші елементи не змінюють масштаб карти.

### 5.2 UTM

- Dropdown містить EPSG:32635 (UTM 35N), EPSG:32636 (UTM 36N), EPSG:32637 (UTM 37N).
- Початкову зону визначати за polygon geopoint вибраного завдання з найменшим ObjectID. Перепроєктувати геометрію точки у WGS 84 geographic для читання довготи:
  - 35N: `24°E ≤ longitude < 30°E`;
  - 36N: `30°E ≤ longitude < 36°E`;
  - 37N: `36°E ≤ longitude < 42°E`.
- Поза цим покриттям показати попередження, вимагати ручного вибору і не робити мовчазного припущення.
- Користувач може змінити зону вручну; при цьому зберігати print scale та позначене компонування, перепроєктувати print view, перевірити підтримку просторової системи всіма map/basemap layers.
- Не переписувати геометрію у Feature Services лише через перемикання WKID відображення.

### 5.3 Сітка і координатні підписи

- UTM-сітка вирівнюється по кратних Easting/Northing вибраної UTM-зони, а не від лівого нижнього кута рамки.
- Для масштабу `1:N` відстань між лініями через 1 мм паперу дорівнює `N × 0.001 м` на місцевості. Наприклад, на `1:1000` це 1 м; кожна десята лінія — через 10 мм паперу.
- Лінії через 1 мм: тонкі сірі. Кожна десята: чорна, товщина 1 output pixel у цільовому JPEG 300 dpi. Товщини треба задавати у координатах кінцевого output raster, а не CSS/екранних пікселях.
- Сітка рендериться тільки всередині прямокутника map frame і точно clip-иться його межами; жодна лінія не виходить за рамку.
- Значення UTM Easting/Northing у метрах підписуються за рамкою для кожної 10-мм лінії. Якщо підписи накладаються, застосувати читабельне форматування/чергування, але не змінювати фактичний крок сітки.
- Перераховувати сітку при зміні масштабу, UTM zone, орієнтації, розміру або позиції map frame.

### 5.4 Символи і легенда

- Джерело символів — локальна бібліотека в `public/symbols/registry.json` та assets під нею.
- Запис бібліотеки пов’язує щонайменше `layer key`, поле коду/значення `symbol_code`, тип geometry, SVG або CIM description, назву/текст легенди та атрибутний field для patch label.
- Лінійні знаки без SVG-файлів: `pattern` (паралельні обводки зі зсувом/пунктиром + маркери вздовж/на вершинах) малюється клієнтським CIMLineSymbol — карта, скетч, легенда і шаблони з одного опису; `stroke` лишається простим fallback.
- Шеврони ЛЕП (`pairedArrows`: розмір/дистанція/крок в екранних одиницях) — окремий графічний оверлей біля вершин: крапки — CIM на вершинах, шеврони — пораховані точки за напрямом сегментів. Тому JPEG їх містить автоматично.
- Заміна symbols виконується у клієнтському renderer; не змінювати символіку опублікованих сервісів.
- Складний polygon приклад: контур кладовища — коричневий, 2 screen/output px у відповідному режимі; хрестики — повторюваний шаховий pattern із налаштованим фізичним інтервалом.
- Перш ніж наповнювати каталог, перевірити CIM marker/picture/hatch capabilities, малювання на кількох масштабах, Editor sketch і власну legend. Непідтримуваний/невідомий `symbol_code` має давати контрольоване попередження.
- Вбудований ArcGIS Legend не є джерелом істини для власного макета. Власна легенда показує patch + значення узгодженого атрибута.
- Дублікати evidence (один `symbol_code` з 2+ різними `legend_decr`) нумеруються за абеткою опису: чорна цифра висотою в половину знака внизу справа — тим самим текстовим оверлеєм на карті (прямо, незалежно від `symbol_angle`) і запеченим PNG-патчем у легенді. Порожній код, невідомі та hidden — без бейджів.

### 5.5 JPEG export

- Дочекатися стабільного MapView та завершення актуалізації шарів.
- Експортувати map frame у фізичних розмірах/масштабі макета, далі скомпонувати з фоном, рамкою, UTM-grid, координатними написами, назвою/task_code, scale bar, north arrow, legend та обов’язковою атрибуцією.
- Включити зазначені елементи у JPEG; не включати інтерфейс редагування/вкладки/панелі.
- Перевірити точний output width/height та збереження масштабу після експорту й фізичного друку на 100%.
- Врахувати обмеження canvas/CORS і cross-origin шарів. Якщо джерело блокує screenshot/canvas, повідомити детальну помилку; не вивантажувати неповний/неправильно масштабований JPEG мовчки.

## 6. Нефункціональні вимоги й безпека

- Публікування: статичний React + TypeScript + Vite SPA у GitHub Pages через GitHub Actions.
- Вхід: Portal OAuth authorization code + PKCE; SSO надає Portal/IdP. Ніяких client secrets, service credentials чи токенів у коді/commit/logs.
- Доступ до WebMap, Feature Services і операцій редагування визначається Portal item sharing, групами та service capabilities. Frontend-прапорець `enabled: false` не є авторизаційним захистом.
- Не логуємо токени. Помилки для UI редагуються від секретних query parameters.
- Високий обсяг task-кодів та related GlobalID фільтрів вимагає батчування ID й перевірки maxRecordCount/REST relationship support; не формувати безмежний SQL `IN (...)`.
- UI має зберігати доступність картографічного canvas під час завантаження Editor та змін розміру viewport.

## 8. Критерії приймання

1. Користувач без організаційної сесії проходить Portal SSO і повертається в застосунок; неавторизований користувач не отримує приватних даних.
2. WebMap відкриває задані 8 логічних шарів; недоступний layer має зрозуміле повідомлення з його ключем/назвою.
3. Вибір task_code фільтрує task, evidence, task geopoint, task polygon і polygon geopoint за зв’язками GlobalID, та виконує zoom до відповідних task polygons.
4. Editor дозволяє дозволені операції тільки на Topo layers, тільки атрибутне оновлення на Evidence; серверні capabilities перевірено.
5. Завантаження/розгортання Editor не змінює розмір viewport застосунку й не ховає/не стискає карту за межі доступного екрана; потрібні панелі прокручуються самостійно.
6. Print view має власний task context, scale, UTM, frame; зміна UTM не змінює вихідну геометрію даних.
7. 1 мм на аркуші відповідає одному grid кроку; кожна десята лінія відрізняється стилем, сітка обрізана по frame, 10 мм coordinate labels правильні.
8. JPEG розмірів A4/300 dpi містить карту, сітку, labels і layout graphics, має перевірений scale; UI виключений.

## 9. Відкриті питання

- Які точні поля/домени містять `symbol_code`; який атрибут має показувати legend label і якою мовою.

- Остаточний відступ рамки карти/місце назви, legend та scale bar.
